## 1. 목적과 원칙

Tailnet 안에서만 접근하는 1인용 웹 워크벤치를 만든다. 빠른 불렛 기록, 비공개 글, 회고, 공개 블로그 초안 작성을 한 흐름으로 제공하되 **원본 데이터는 사람이 읽고 Git으로 관리하는 Markdown 파일**로 남긴다.

설계 원칙:

1. **파일이 원본이다.** 앱은 파일 위에 있는 얇은 뷰다. 앱이 사라져도 데이터는 그대로 읽힌다.
2. **의도적 마찰을 보존한다.** 이월·완료·발행은 자동화하지 않는다. 사람이 가치를 다시 판단하는 장치로 남긴다.
3. **경계는 물리적으로 강제한다.** 공개/비공개, 코드/콘텐츠, 읽기/쓰기 경계를 코드 규약이 아니라 파일시스템·프로세스 경계로 막는다.
4. **실패 시 원본을 보존한다.** 어떤 실패도 원본 Markdown을 훼손하지 않는다.
5. **최소 스택.** 1인 Tailnet 서비스에 맞는 최소 구성. 규모·자동화·프레임워크 무게를 늘리지 않는다.

M1 비목표: 다중 사용자·CRDT·실시간 동기화, AI 자동 분류/요약/자동 발행, 자동 이월, 모바일 네이티브 앱, 생산성 점수·대시보드, 템플릿 내부 실행형 스크립트, 자동 push/배포.

## 2. 세 개의 저장소 경계 (핵심 결정)

이전 설계 트리는 `inbox/ journal/ notes/...` 를 앱 저장소 루트에 그려 **앱 코드와 사용자 콘텐츠를 한 저장소에 섞는 것처럼** 보였다. 이는 코드 커밋과 기록 커밋 이력이 뒤엉키고, 배포 산출물이 개인 기록과 같은 히스토리에 남는 문제를 만든다. 재평가 결과 **세 개의 독립된 트리**로 분리한다(§12 D1).

```text
① personal-workbench (이 저장소, private) — 애플리케이션 코드 + 문서
   src/core/        순수 도메인 (I/O 의존 없음: 파싱, 이월 정책, 발행 검증)
   src/server/      어댑터 (파일·Git·public clone) + HTTP 경계
   src/web/         React 클라이언트 (core/server의 API만 소비)
   docs/            스펙·계획·운영 문서
   → 사용자 콘텐츠를 절대 추적하지 않는다.

② WORKSPACE_ROOT (별도 디렉터리, 그 자체가 독립 Git 저장소, private)
   inbox/           빠른 캡처
   journal/         일일 불렛 노트 (YYYY/MM/YYYY-MM-DD.md)
   notes/           장기 메모·프로젝트 노트
   drafts/          비공개 글과 발행 후보
   reviews/         weekly/, monthly/ 회고
   templates/       사용자 소유 Markdown 템플릿
   assets/          비공개 첨부 (assets/private/ 는 절대 공개 금지)
   → 앱은 이 트리를 읽고 쓴다. 기록 이력은 이 저장소의 Git이 담당한다.

③ PUBLIC_BLOG_ROOT (blog.gze1206.net 의 읽기 전용 clone)
   src/content/posts/**/*.mdoc   ← 발행 경로. 앱이 유일하게 쓰는 하위 경로.
   → 그 외 전부 읽기 전용. 앱은 이 저장소에 절대 push 하지 않는다.
```

경계 규칙:

- 앱 저장소(①)와 콘텐츠 저장소(②)는 분리된 Git 트리다. ②는 ①의 서브모듈이 아니다. 이로써 코드 이력과 기록 이력이 섞이지 않고, 앱을 재설치해도 기록은 자기 저장소에 남는다.
- 공개(③)와 비공개(②)는 절대 같은 저장소에 두지 않는다. 발행은 ②→③ 단방향 수동 작업이다.
- private 원본·첨부·Git 이력·내부 링크가 ③에 섞이는 기능은 만들지 않는다.
- 앱은 ③을 **발행 경로(`src/content/posts/`)를 제외하면 읽기 전용**으로만 다룬다. 자격 증명도 그렇게 최소화한다(§10).

## 3. 최소 스택 (핵심 결정)

이전 초안 계획은 Next.js App Router를 골랐다. 재평가 결과 1인 Tailnet 서비스에는 과하다고 판단하고 더 가벼운 구성을 택한다(§12 D2).

**확정 스택**

| 층          | 선택                                                | 근거                                                                                          |
| ----------- | --------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| 언어        | TypeScript strict                                   | 도메인 계약을 타입으로 고정                                                                   |
| 클라이언트  | Vite + React 19                                     | 키보드 우선의 앱형 상호작용에 적합, 공개 블로그(Astro/Vite/Tailwind v4/React19) 툴체인 재사용 |
| 서버        | Hono (Node 런타임, 단일 프로세스)                   | 최소 HTTP 경계. 빌드된 클라이언트와 API를 한 `node` 프로세스로 서빙                           |
| 스타일      | Tailwind v4                                         | 블로그와 동일                                                                                 |
| 검증        | Zod                                                 | frontmatter·입력·발행 계약 검증                                                               |
| frontmatter | `gray-matter` (+ `yaml`)                            | 파싱/직렬화, 미해석 필드 라운드트립 보존                                                      |
| Git         | Git CLI를 감싼 얇은 어댑터 (`simple-git` 선택 가능) | 결정적·검증 가능                                                                              |
| 테스트      | Vitest(단위/통합) + Playwright(최소 e2e)            | 블로그와 동일한 Vitest                                                                        |
| 배포        | 단일 Docker 컨테이너 + Tailscale Serve              | §10                                                                                           |

**기각안**: Next.js App Router — 프레임워크 무게가 크고 edge 런타임 유혹과 서버/클라 경계 혼동을 부른다. 순수 파일·Git I/O만 필요한 1인 서비스에는 Vite+Hono가 더 작고, 도메인 계층을 프레임워크에서 완전히 분리하면 웹 계층은 언제든 교체 가능하다.

**데이터베이스 없음(M1).** 원본은 파일이다. 검색·목록을 위한 인덱스는 **부팅 시 frontmatter 스캔으로 만드는 재생성 가능한 인메모리 인덱스**로 한정한다. 영속 DB는 도입하지 않는다. 규모가 커지면 SQLite를 *재생성 가능한 캐시*로만 뒤에 붙일 수 있으나 원본 지위는 절대 주지 않는다(§12 D3).

## 4. 계층 구조와 깊은 도메인 모듈

```text
src/web (React)  ──HTTP──▶  src/server (Hono 라우트, 얇음)
                                  │ 호출
                                  ▼
                            src/core (순수 도메인, 깊은 모듈)
                                  │ 포트(interface)로 의존
                                  ▼
                     src/server/adapters (fs, git, publicBlog)
```

- `src/core` 는 파일시스템·Git·HTTP를 모른다. 문자열 in / 문자열·결정(decision) out. 이월 정책, 불렛 파서, 발행 검증, 회고 기간 계산이 여기 산다. 대부분의 테스트가 여기서 빠르게 돈다.
- `src/server/adapters` 는 포트 인터페이스(`FileStore`, `GitRepo`, `PublicBlog`)를 구현한다. 원자적 저장·Git·clone 접근의 유일한 창구다.
- `src/server` 라우트는 얇다. 입력 검증(Zod) → core 호출 → adapter 실행 → 결과 반환.
- `src/web` 는 서버 API만 소비하고 **검증되지 않은 원시 파일시스템 경로를 절대 받지 않는다.**

이 경계 덕에 core는 프레임워크·I/O 없이 단위 테스트되고, 웹/서버 계층은 교체 가능한 얇은 껍데기가 된다.

## 5. Markdown / Frontmatter 문법

### 5.1 공통 규칙

- 모든 개인 문서는 **Markdown + YAML frontmatter**다.
- 앱은 **닫힌(closed) 필드 집합만 해석**한다. 그 외 필드는 **해석하지 않되 라운드트립으로 보존**한다(사용자가 손으로 넣은 필드를 앱이 삭제하지 않는다).
- 직렬화는 **정규(canonical) 형태**로 고정한다: 키 순서 고정, 2-스페이스 들여쓰기, 날짜는 `YYYY-MM-DD`, 문자열 배열은 `['a', 'b']` 흐름 스타일. 파서는 관대하게, 직렬화기는 정규로 → Git diff가 최소가 되고 파일이 손으로도 안전하게 읽힌다.

### 5.2 문서 종류(`kind`)와 최소 frontmatter

앱이 해석하는 필드는 종류별로 다음이 전부다.

**공통**: `title`(string), `kind`(enum), `createdAt`(date), `updatedAt`(date).

| kind             | 추가 해석 필드                          | 기본 경로                       |
| ---------------- | --------------------------------------- | ------------------------------- |
| `capture`        | —                                       | `inbox/`                        |
| `journal`        | `date`(YYYY-MM-DD)                      | `journal/YYYY/MM/YYYY-MM-DD.md` |
| `note`           | `tags?`(string[])                       | `notes/`                        |
| `private-post`   | `tags?`                                 | `drafts/`                       |
| `public-draft`   | `publicEligible`(bool), 발행 필드(§9.1) | `drafts/`                       |
| `weekly-review`  | `period`(YYYY-Www)                      | `reviews/weekly/`               |
| `monthly-review` | `period`(YYYY-MM)                       | `reviews/monthly/`              |

`kind` 는 enum이며 미지원 값은 파싱 오류다.

### 5.3 템플릿 문법

템플릿은 `templates/` 아래 일반 Markdown이다. 앱이 해석하는 템플릿 frontmatter는:

- `title`: 템플릿 목록 표시 이름
- `kind`: 위 문서 종류
- `defaultPath`: 새 문서 기본 저장 위치(WORKSPACE_ROOT 상대, §7 안전 규칙 통과 필수)
- `publicEligible`: 공개 Markdoc 변환 가능 여부

본문은 제목·질문·체크리스트·불렛 골격을 자유롭게 담는다. 템플릿에서 문서를 생성하면 본문을 새 문서로 복제하고 **새 문서에만 필요한 메타데이터(날짜·식별자·period)만** 채운다. 템플릿 본문의 토큰 치환은 `{{date}}`, `{{isoDate}}`, `{{period}}`, `{{id}}` 만 지원한다(실행형 스크립트 없음).

초기 기본 템플릿 5종: 빠른 메모(capture), 비공개 글(private-post), 공개 글 초안(public-draft), 주간 회고(weekly-review), 월간 회고(monthly-review). 앱에서 복제·편집·추가할 수 있으나 결과는 언제나 파일로 저장한다.

## 6. 키보드 우선 불렛 문법

첫 화면은 오늘의 일일 로그다. 키보드만으로 항목을 빠르게 추가·전이한다.

### 6.1 정규 한 줄 직렬화

```md
- • 배포 메모 <!-- wb:id=01HX7... -->
- – LCP 관련 참고 노트 <!-- wb:id=01HX8... -->
- ○ 14:00 회고 세션 <!-- wb:id=01HX9... -->
- □ 공개 글 초안 정리 <!-- wb:id=01HXA... -->
- ▣ 배포 스크립트 정리 <!-- wb:id=01HXB... --> (완료된 할 일)
- ⨯ 접힌 아이디어 <!-- wb:id=01HXC... --> (취소)
```

- 유형 글리프: `•` 메모, `–` 노트, `○` 일정, `□` 할 일.
- 상태: 할 일 `□`(열림) / `▣`(완료) / `⨯`(취소). 완료·취소는 명시적 사용자 행동으로만 바뀐다.
- 각 항목은 안정적 `<!-- wb:id=<ULID> -->` 를 갖는다. ID는 이월·회고 링크의 앵커이며, 한 번 부여되면 바뀌지 않는다.
- 표준 Markdown 리스트(`- `) 위에 글리프를 얹어, 앱 밖에서도 리스트로 읽힌다.

파서는 관대하다(글자 사이 공백 변형, 사용자가 손으로 쓴 글리프 없는 줄도 메모로 수용). 직렬화기는 위 정규형으로만 쓴다.

### 6.2 입력 규칙

- 화면은 기본값이 오늘 로그다. 빠른 캡처는 별도 메모 화면으로 가지 않고 오늘 로그에서 시작한다.
- 유형 삽입 단축키로 `•`·`–`·`○`·`□` 를 최소 조작으로 지정한다.
- Enter 로 다음 항목, 상태 토글 단축키로 완료/취소, 유형 변경 단축키로 글리프 순환.

## 7. 원자적 저장

모든 쓰기는 원본을 절대 부분 훼손하지 않는다.

1. 대상과 **같은 디렉터리**에 임시 파일(`.<name>.<rand>.tmp`) 작성.
2. 내용 write 후 `fsync`.
3. 임시 파일 → 대상 경로로 **원자적 `rename`**. (같은 파일시스템 보장)
4. 디렉터리 `fsync`(가능 플랫폼).

동시성: 워크스페이스당 **단일 라이터**를 전제하되, 프로세스 내 쓰기는 경로별 큐(직렬화)로 보호한다. 크로스 프로세스 안전을 위해 워크스페이스 루트에 어드바이저리 락 파일을 둔다.

경로 안전(모든 계층 공통):

- 모든 상대 경로는 `WORKSPACE_ROOT`(또는 발행 시 `PUBLIC_BLOG_ROOT/src/content/posts`) 안으로 `realpath` 해석 후 **루트 밖이면 거부**한다.
- 심볼릭 링크 탈출, `..` 탈출, 절대 경로 주입을 거부한다.
- 클라이언트는 검증된 논리 식별자만 다루고 원시 경로를 만들지 않는다.

DB로의 원본 복제는 하지 않는다(§3). 인덱스는 파일에서 언제든 재생성한다.

## 8. Git 경계와 이월

### 8.1 Git 경계 (핵심 결정)

- **콘텐츠 저장(②)은 평범한 원자적 파일 쓰기다. Git 커밋은 키 입력마다 자동으로 일어나지 않는다.** 커밋은 사용자가 누르는 명시적 "스냅샷" 행동이다(§12 D4). Git은 이력만 담당한다.
- 앱은 **어떤 저장소에도 자동 push 하지 않는다.**
- 커밋 메시지·범위는 사용자가 확인한다. 대량 자동 커밋으로 이력을 오염시키지 않는다.
- 충돌·더러운 워크트리는 변경을 중단하고 원인·경로·재시도 방법을 보여 준다.

### 8.2 의도적 이월

날짜가 바뀌어도 미완료 항목을 **자동 복제·자동 이월하지 않는다.** 이전 일지 항목은 원래 위치에 남고, 사용자가 검토 패널에서 발견한다.

두 가지 이월 방식:

1. **간편 이월**: 항목 선택 → 이월 → 대상 날짜 확인.
2. **의식적 이월**: 짧은 확인 문구 입력 → 대상 날짜 확인.

두 방식 모두 **양방향 불변 이력**을 남긴다:

- 원본 줄: `<!-- wb:migrated-to=<newId> at=<date> -->` 추가(원본 텍스트는 보존).
- 새 항목: `<!-- wb:migrated-from=<oldId> -->` 포함.

`migrateBullet({ sourceId, targetDate, mode: 'quick' | 'intentional', confirmation })` 는 의식적 모드에서 확인 문구가 없으면 거부한다. 완료·취소·노트화·비공개 글 초안 승격도 모두 명시적 사용자 행동이다.

## 9. 안전한 공개 Markdoc 발행

공개 글 초안은 ②에서 작성한다. `publicEligible: true` 문서만 발행 대상이 된다. 발행은 아래 게이트를 **순서대로** 통과한 뒤에만 ③의 작업 브랜치에 커밋을 만든다. 자동 push·자동 배포는 없다.

### 9.1 목표 계약 (공개 블로그 실제 스키마에 고정)

공개 블로그는 Astro + Markdoc, 콘텐츠는 `src/content/posts/**/*.mdoc`, 스키마는:

```
title: string
description: string
slug: /^[a-z0-9]+(?:-[a-z0-9]+)*$/     (소문자·숫자·하이픈, 양끝/연속 하이픈 금지)
category: string
tags: string[]  (최소 1개)
series?: string        ┐ 둘 다 있거나
seriesOrder?: int > 0  ┘ 둘 다 없어야 함
publishedAt: date
updatedAt: date
draft: boolean (기본 false)
```

발행기는 이 계약을 Zod로 재현해 변환 전에 검증한다. 스키마 불일치는 발행을 중단시킨다.

### 9.2 발행 파이프라인 (5 게이트)

1. **메타데이터 확인**: 제목·slug·category·tags·publishedAt·updatedAt(·series/seriesOrder)을 확정. slug 패턴, tags≥1, series/seriesOrder 동반 규칙 검증.
2. **공개 범위 검사(누출 탐지)**: 본문·frontmatter에서 `file://`, `workspace/`, `assets/private/`, 설정된 private 루트 경로, 내부 위키 링크(`[[...]]`), 미해결 자산 참조를 거부한다. 허용된 자산만 public 스테이징으로 복사한다.
3. **결정적 변환**: 승인된 frontmatter → `postSchema` 형태의 `.mdoc` 생성. 같은 입력은 항상 같은 출력. 생성물은 Git 작업 전에 스키마 재검증.
4. **드라이런 미리보기**: `content/<slug>` 대상 경로와 **통합 diff**를 보여 준다. 이 단계는 ③의 워크트리·Git 상태를 **전혀 바꾸지 않는다.**
5. **명시적 확정 커밋**: ③ 워크트리가 깨끗할 때만 진행. `confirmPublish: true` 를 받은 뒤 `content/<slug>` 브랜치를 만들고 `.mdoc`(+허용 자산)를 커밋한다. **push 하지 않는다.**

실패(누출 탐지·스키마·더러운 워크트리·변환)는 커밋을 만들지 않고 원인·파일·재시도 방법을 보여 준다.

### 9.3 기존 블로그 CMS 전환 참고

공개 블로그의 동적 작성 경로(구 CMS UI/API/Worker 브리지/GitHub App 변수) 제거는 별도 일감에서 다룬다. 이 워크벤치는 유일한 작성·발행 진입점이 되고, 공개 블로그는 정적 렌더링만 담당한다. 기존 `.mdoc` 글과 profile·experience 콘텐츠는 계속 공개 블로그가 렌더링한다. **이 스펙 작업은 공개 블로그 저장소를 수정하지 않는다.**

## 10. Tailnet 운영 경계

- **단일 Docker 컨테이너**, 전용 **비루트 서비스 계정**으로 실행.
- 노출은 **Tailscale Serve로 tailnet 전용**. 공개 인터넷/`0.0.0.0` 바인딩 금지(루프백 + Tailscale만).
- 자격 증명 최소화: ②에 대한 read/write 키, ③에 대한 **발행 경로를 제외하면 읽기 전용** clone 자격.
- `GET /api/health`: 준비 상태만 보고하고 **비밀 값·경로를 노출하지 않는다.**
- **시작 시 설정 검증**: 루트 미설정, private/public 루트가 같음, 설정 루트 밖의 쓰기 가능 디렉터리, ②·③ 경로 겹침을 거부한다.
- 백업/복구: 백업은 ②·③가 각자 Git이므로 Git이 1차 수단. 컨테이너는 상태를 갖지 않는다(인덱스는 재생성). 문서에 백업·복구 명령을 남긴다.
- **자동 배포 금지**: Serve/ACL 적용과 개인 서버 배포는 사용자의 외부 작업 최종 승인 없이는 하지 않는다.

## 11. 테스트 전략

TDD: 각 단위는 실패하는 테스트를 먼저 쓴다. 테스트 피라미드:

- **순수 도메인 단위(Vitest, 다수)**: 템플릿·불렛 파서/직렬화, 이월 정책(자동 이월 없음, 양방향 이력), 회고 기간 계산, 발행 검증(누출·slug·series 규칙), frontmatter 라운드트립(미해석 필드 보존). I/O 없음, 빠름.
- **어댑터 통합(Vitest, 임시 디렉터리/임시 Git 저장소)**: 원자적 rename·크래시 안전, 경로 탈출 거부, Git 스냅샷/브랜치 커밋, 더러운 워크트리 거부, 드라이런이 워크트리를 바꾸지 않음.
- **API 통합(얇게)**: 라우트 입력 검증과 오류 형태.
- **Playwright e2e(최소)**: 키보드 캡처, 자동 이월 없음, 간편·의식적 이월 다이얼로그, 회고 제안이 앱 열 때만 뜸, 발행 확정 전 미변경.

고정할 검증 기준(설계에서 승계):

- 템플릿 생성 시 본문·메타데이터가 의도한 경로에 생성된다.
- 날짜 경계에서 미완료 항목이 자동 이월되지 않는다.
- 간편·의식적 이월 모두 원본·새 항목의 연결 이력을 남긴다.
- 회고 제안은 앱을 연 시점에만 발생하고 문서를 자동 생성하지 않는다.
- private 링크·경로·자산을 포함한 초안은 공개 변환을 거부한다.
- 공개 변환은 확정 전 public 저장소를 변경하지 않는다.

CI 게이트: `pnpm test && pnpm lint && pnpm format:check && pnpm build && pnpm e2e`.

## 12. 결정 기록 (ADR 요약)

- **D1 — 세 저장소 분리.** 앱 코드(①)·콘텐츠(②)·공개 블로그 clone(③)을 독립 트리로 나눈다. 이전 트리가 콘텐츠를 앱 루트에 둔 모호함을 해소. 근거: 코드/기록 이력 분리, 재설치 내구성, 공개/비공개 물리적 차단. ②는 ①의 서브모듈이 아니다.
- **D2 — Vite + React + Hono(Node), Next.js 기각.** 1인 Tailnet 서비스에 Next.js는 과함. 도메인을 프레임워크에서 분리해 웹 계층을 교체 가능하게 유지.
- **D3 — M1 DB 없음.** 원본은 파일. 인덱스는 부팅 시 재생성하는 인메모리. 영속 저장은 도입하지 않으며, 훗날 SQLite도 재생성 캐시로만.
- **D4 — Git 커밋은 명시적 스냅샷.** 콘텐츠 저장은 원자적 파일 쓰기, 커밋은 사용자 행동. 자동 커밋/자동 push 없음.
- **D5 — 발행 계약을 공개 블로그 실제 postSchema에 고정.** slug 정규식, tags≥1, series/seriesOrder 동반 규칙을 발행기가 그대로 재현. 드라이런은 워크트리 불변, 확정 후에도 push 없음.
- **D6 — 미해석 frontmatter 라운드트립 보존.** 앱이 모르는 필드를 삭제하지 않는다. 파일 소유권은 사용자에게.

## 13. 오류 처리

원본 파일은 실패 시에도 보존한다. frontmatter 오류, 템플릿 파싱 실패, 경로 탈출, Git 충돌, Markdoc 변환 실패, 공개 범위 검사 실패는 **변경을 중단**하고 원인·파일 위치·재시도 방법을 보여 준다. 부분 저장은 발생하지 않는다(원자적 rename).
