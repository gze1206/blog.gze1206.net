# 0018. 워크벤치 아키텍처 결정 D1~D6

## 맥락 (Context)

워크벤치 아키텍처 스펙([2026-08-12-personal-workbench-architecture.md](../spec/workbench/2026-08-12-personal-workbench-architecture.md))은
§12 에 결정 여섯 개(D1~D6)를 요약해 두었다. 이 결정들은 워크벤치가 별도 private 저장소에 있을 때 그 저장소
안의 문서로만 남아 있었다. 워크벤치가 이 저장소로 들어오면서(ADR 0017) 저장소 공통 ADR 로 옮긴다. 결정의
상세 근거는 원 스펙의 해당 절에 그대로 있다.

옮기면서 D1 은 ADR 0017 에 맞춰 개정하고, D5 는 1a(NOR-195)에서 바뀐 계약 위치를 반영한다. 나머지는 원문의
뜻을 그대로 옮긴다.

## 검토한 대안 (Options)

- **D2 대안(Next.js App Router)**: 앱형 상호작용과 서버를 한 프레임워크로 묶을 수 있지만, 1인 Tailnet
  서비스에는 프레임워크 무게가 크고 서버·클라이언트 경계를 흐린다(원 스펙 §3).
- **D3 대안(영속 DB)**: 검색·목록이 빨라지지만 파일 외에 두 번째 원본이 생긴다.
- **D4 대안(저장할 때마다 자동 커밋)**: 이력이 빠짐없이 남지만 이력이 잡음으로 덮이고 사용자 확인이 빠진다.
- **D6 대안(앱이 아는 필드만 직렬화)**: 구현은 단순하지만 사용자가 손으로 넣은 필드를 지운다.

D1·D5 의 대안은 아래 결정의 개정 내용과 ADR 0017 을 따른다.

## 결정 (Decision)

- **D1: 앱 코드와 개인 기록을 분리한다.** 앱 코드(①)는 공개 블로그(③)와 같은 저장소에 산다(ADR 0017).
  개인 기록(②, WORKSPACE_ROOT)의 분리는 유지한다. ②는 독립 Git 저장소이며 ①의 서브모듈이 아니다. 앱은
  실행 시 ③을 별도 clone(PUBLIC_BLOG_ROOT)으로 다루고, 발행 경로(`BLOG_LAYOUT.postsDir`) 밖은 읽기 전용이다.
  공개(③)와 비공개(②)는 같은 저장소에 두지 않는다.
- **D2: Vite + React + Hono(Node)를 쓰고 Next.js 는 쓰지 않는다.** 도메인(`src/core`)을 프레임워크에서
  분리해 웹 계층을 교체할 수 있게 둔다.
- **D3: M1 에는 DB 가 없다.** 원본은 파일이다. 인덱스는 부팅할 때 다시 만드는 인메모리 인덱스이며, 나중에
  SQLite 를 붙이더라도 재생성 가능한 캐시로만 쓴다.
- **D4: Git 커밋은 명시적 스냅샷이다.** 콘텐츠 저장은 원자적 파일 쓰기이고, 커밋은 사용자 행동이다. 자동
  커밋과 자동 push 는 없다.
- **D5: 발행 계약은 공개 블로그의 실제 `postSchema` 에 고정한다.** 1a 부터 워크벤치는 규칙을 복제하지 않고
  `@gze1206/content-contract` 의 `strictPostSchema`(블로그 `postSchema` 와 같은 규칙에 모르는 키 거부를 더한
  것)를 쓴다. 드라이런은 워크트리를 바꾸지 않고, 확정한 뒤에도 push 하지 않는다.
- **D6: 앱이 해석하지 않는 frontmatter 는 라운드트립으로 보존한다.** 앱이 모르는 필드를 지우지 않는다.
  파일 소유권은 사용자에게 있다.

## 근거 (Rationale)

- D1: 코드 이력과 기록 이력을 섞지 않고, 앱을 다시 설치해도 기록은 자기 저장소에 남는다. 공개 코드와 같은
  저장소에 살더라도 개인 기록은 물리적으로 다른 트리이므로 공개·비공개 차단은 그대로다. 저장소를 합친 근거는
  ADR 0017 에 있다.
- D2·D3: 1인 Tailnet 서비스에 맞는 최소 스택이다. 순수 파일·Git I/O 만 필요하다.
- D4: 이월·완료·발행 같은 의도적 마찰을 보존하는 원칙(원 스펙 §1)을 Git 에도 적용한다.
- D5: 발행기가 블로그와 다른 규칙을 쓰면 발행한 글이 블로그 빌드에서 깨진다. 1a 이전에는 복제본이 `toc` 를
  몰라 실제로 그런 일이 생겼다. 같은 객체에서 파생하면 필드 추가가 양쪽에 동시에 반영된다.
- D6: 파일이 원본이고 앱은 그 위의 얇은 뷰라는 원칙(원 스펙 §1)을 지킨다.

## 영향 (Consequences)

- 긍정: 워크벤치 결정이 블로그 ADR 과 같은 목록에서 번호로 추적된다.
- 긍정: D5 의 계약 단일화로 발행 결과가 블로그 스키마를 통과하는지 계약 테스트(NOR-195 AC-8, AC-9)가 지킨다.
- 비용: 원 스펙 §12 와 이 ADR 이 겹친다. 원 스펙 §12 에는 이 ADR 로 옮겼다는 안내를 두고, 이후 개정은 이
  ADR 에만 한다.
- 후속 작업: WORKSPACE_ROOT 저장소 생성과 워크벤치 배포는 NOR-198 에서 다룬다.
