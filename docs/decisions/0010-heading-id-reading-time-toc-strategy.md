# 0010. 헤딩 id 규칙 · 읽기 시간 산정 · 목차/스크롤 스파이 전략

## 맥락 (Context)

NOR-17 은 글 상세에 **헤딩 앵커 · 목차(TOC) · 읽기 시간**을 붙인다. 셋 다 나중에 바꾸면
비용이 큰 결정을 하나씩 품고 있다.

1. **헤딩 id** — `https://gze1206.net/blog/foo#설치하기` 는 남이 저장하고 공유하는 **영구 주소**다.
   규칙을 나중에 바꾸면 기존 링크가 조용히 깨진다.
2. **읽기 시간** — 표시된 숫자는 독자의 기대를 만든다. 산정 방식이 흔들리면 같은 글의 표기가
   빌드마다 달라진다.
3. **렌더 경로가 둘이다** — 이 저장소는 `.md` 와 `.mdoc` 을 함께 받는다(ADR 0003).
   `.md` 는 remark/rehype 파이프라인을, `.mdoc` 은 Markdoc 자체 렌더러를 탄다.
   **두 경로는 서로의 플러그인을 전혀 공유하지 않는다.** 현재 발행 글은 전부 `.md` 지만,
   CMS(Keystatic, NOR-19/20)가 Markdoc 을 쓰므로 앞으로 쓰는 글은 `.mdoc` 이 된다.

## 검토한 대안 (Options)

### A. 헤딩 id 생성 규칙

- **A-1. 각 렌더러의 기본값(github-slugger)에 맡긴다** — 코드 0줄.
  단, `.md` 는 Astro 의 `rehypeHeadingIds`, `.mdoc` 은 `@astrojs/markdoc` 의 heading 노드가
  **각자** github-slugger 를 부르는 구조다. 지금 우연히 같을 뿐 계약이 아니고, 어느 한쪽
  패키지가 규칙을 바꾸면 그날부터 두 경로의 주소가 갈라진다. 게다가 `C#` → `c` 가 되어
  카테고리·태그 슬러그(`src/lib/slug.ts`, ADR 0009)의 `c-sharp` 과도 어긋난다.
- **A-2. `toSlug`(ADR 0009)를 재사용해 저장소 안에 규칙을 고정하고, 두 렌더 경로가 같은 함수를 쓴다.**
  코드가 조금 늘지만 규칙이 한 곳에 있고 단위 테스트로 고정된다.

### B. 읽기 시간 산정

- **B-1. 공백 기준 단어 수 ÷ 200** — 가장 흔한 구현. 한국어에서 크게 빗나간다. 한국어는 어절이
  짧고 조사·어미가 붙어 어절당 정보량이 영어 단어와 다르다. 이 블로그 본문은 대부분 한국어다.
- **B-2. 전부 글자 수로 센다** — 영문 비중이 큰 글(코드 설명·용어 나열)에서 반대로 빗나간다.
- **B-3. 문자 종류별로 나눠 각각 다른 속도를 적용하고, 코드블럭은 따로 가산한다.**

### C. 목차 배치와 스크롤 스파이

- **C-1. 데스크톱 고정 사이드바 + 모바일 접힘** — 흔한 형태. 본문과 사이드바를 한 그리드에
  놓으려면 DOM 순서(제목 → 본문)와 시각 배치가 어긋나고, 모바일/데스크톱에서 접힘 상태가
  달라야 해서 CSS 만으로는 정직하게 만들기 어렵다(`<details>` 의 열림 상태는 CSS 로 못 바꾼다).
- **C-2. 본문 위 인라인 목차 + 좁은 화면에서 높이 제한.** DOM 순서가 곧 읽기 순서이고,
  JS 가 없으며, 높이가 CSS 로 고정돼 레이아웃이 움직이지 않는다.
- **스크롤 스파이**는 별개 선택지다. IntersectionObserver 로 현재 절을 목차에 표시하는 향상.

## 결정 (Decision)

1. **헤딩 id 는 `toSlug`(ADR 0009) 를 재사용해 저장소에서 만든다(A-2).** 중복은 등장 순서대로
   `-2`, `-3` 을 붙여 결정적으로 유일화한다. `.md` 는 rehype 플러그인이, `.mdoc` 은 Markdoc
   `nodes.heading` 오버라이드가 **같은 `createHeadingIdFactory`** 를 쓴다.
2. **읽기 시간은 문자 종류별 혼합 산정(B-3)** 으로 한다. 한글·CJK **500자/분**, 라틴 **200단어/분**,
   코드블럭 **40줄/분(블럭당 30줄 상한)**. 수식·이미지·캡션·프론트매터·Markdoc 태그 속성값은 제외한다.
   최소 표기는 `1분 미만`이고 기계값(ISO 8601)은 `PT1M` 으로 바닥을 친다.
3. **목차는 본문 위 인라인 배치(C-2)**, `h2`~`h3` 두 단계, 담을 헤딩이 2개 미만이면 렌더하지 않는다.
4. **스크롤 스파이는 하지 않는다.**

## 근거 (Rationale)

### 헤딩 id

- 한 사이트 안에서 `#설치하기` 와 `/tags/웹-성능` 이 **다른 규칙**으로 만들어지면 설명할 수 없다.
  같은 `toSlug` 를 쓰면 유니코드 보존·`C#`→`c-sharp` 음차·NFKC 정규화가 자동으로 따라온다.
- `toSlug` 는 결과가 비면 예외를 던지지만(`EmptySlugError`), 헤딩에서는 던지지 않고
  `section` 으로 떨어뜨린다. `## ???` 하나 때문에 글 전체 빌드를 세우는 것은 과하다.
- 중복 유일화는 **두 번째 등장이 `-2`** 다(github-slugger 는 `-1`). 사람이 URL 을 보고
  "두 번째 설치하기"로 읽을 수 있다. 이미 발급된 id 와 겹치는 후보는 건너뛰므로,
  본문에 `## 설치` 두 개와 `## 설치 2` 가 섞여 있어도 충돌하지 않는다.
- 이 규칙은 **이 ADR 로 고정**한다. 바꾸려면 새 ADR 을 쓰고 리다이렉트를 함께 계획해야 한다.

### 읽기 시간

- 한국어 묵독 속도는 분당 글자 수로 이야기하는 편이 자연스럽고, 일반 산문 기준 **분당 500자**를
  택했다. 영어는 비문학 묵독 약 240단어/분(Brysbaert 2019 메타분석)이 알려져 있으나, 기술 글은
  더 천천히 읽히므로 **200단어/분**으로 보수적으로 잡았다. 두 값 모두 `src/lib/reading-time.ts`
  상단 상수 하나씩이라 조정 비용이 낮다.
- **코드블럭을 산문 글자로 세면 코드 많은 글의 추정치가 비현실적으로 튄다.** 사람은 코드를
  문장처럼 읽지 않고 훑는다. 그래서 줄 수로 세고(40줄/분), **블럭당 30줄 상한**을 둔다 —
  300줄 덤프를 처음부터 끝까지 읽는 독자는 없다.
- 수식은 제외하고 별도 가산도 하지 않는다. 수식은 글자 수 대비 읽기 시간 편차가 너무 커서
  어떤 상수도 신뢰하기 어렵다. 이미지·캡션·프론트매터·Markdoc 속성값도 본문 분량이 아니다.
  반면 `{% callout %}` **안의 산문은 독자가 읽으므로 센다** — 마커만 걷어낸다.
- **빌드타임 계산**이다. 순수 함수(`estimateReadingTime`)로 두고 단위 테스트로 고정한다.
  런타임 JS 로 세면 크롤러가 못 읽고, 같은 글이 기기마다 다른 값을 보일 수 있다.
- "0분 읽기"는 나올 수 없다. 1분 미만이면 `1분 미만`으로 표기한다.

### 목차

- 인라인 배치는 **DOM 순서가 곧 읽기 순서**(제목 → 메타 → 목차 → 본문)라 스크린리더·키보드
  사용자에게 자연스럽고, 사이드바 그리드처럼 시각 순서와 DOM 순서가 어긋날 여지가 없다.
- 좁은 화면에서는 목록 높이를 `45vh` 로 제한해 긴 목차가 본문을 밀어내지 않게 한다.
  **높이가 CSS 로 고정돼 있고 JS 가 관여하지 않으므로 렌더 후 레이아웃이 움직이지 않는다(CLS 0).**
- `h4` 이하까지 담으면 목차가 본문만큼 길어져 "훑어보기"라는 목적을 잃는다. 글 제목이 `h1`
  이므로 본문 헤딩은 `h2` 부터이고, 실질적으로 `h2`~`h3` 두 단계면 충분하다.
- 헤딩이 0~1개인 글에서 목차는 정보가 아니라 소음이다. 판단은 `buildToc` 한 곳에서 한다
  (빈 배열 → 컴포넌트가 아무것도 렌더하지 않음). 템플릿마다 조건을 복사하지 않는다.

### 스크롤 스파이를 하지 않는 이유

목차가 인라인이라 스크롤하면 화면 밖으로 나간다. **보이지 않는 목차의 현재 위치를 갱신하는 것은
아무에게도 보이지 않는다.** 값을 얻으려면 먼저 목차를 고정(sticky) 배치로 바꿔야 하고, 그것은
위에서 인라인을 택한 이유(DOM 순서·CLS·JS 없음)를 되돌리는 일이다. 즉 스크롤 스파이는 지금
구조에서 **비용만 있고 이득이 없다.** 베이스 테마가 확정되고(NOR-24) 목차를 고정 배치로 옮길 때
다시 판단한다. 그때는 IntersectionObserver 기반 점진적 향상 + `prefers-reduced-motion` 존중이 전제다.

## 영향 (Consequences)

### 긍정

- 헤딩 id 규칙이 **문서와 테스트로 고정**됐고, `.md` / `.mdoc` 두 경로가 같은 함수를 쓴다.
  라이브러리가 기본값을 바꿔도 우리 주소는 흔들리지 않는다.
- 목차 데이터가 **렌더러가 실제로 붙인 id**(`render()` 의 `headings`)에서 나오므로,
  목차 링크와 본문 앵커가 어긋날 수 없다.
- 읽기 시간·헤딩 목록·ISO 날짜가 `derivePostDetail` 한 곳에서 나온다.
  Phase 7(NOR-27~30)의 JSON-LD 는 계산을 다시 만들지 않고 이 값을 그대로 쓴다.

### 부정 / 비용

- **`markdoc.config.mjs` 의 `fence` 트랜스폼을 동기로 바꿔야 했다.** Markdoc 은 자식 트랜스폼이
  하나라도 Promise 를 돌려주면 `Markdoc.transform()` 전체가 Promise 가 되고,
  `@astrojs/markdoc` 의 헤딩 수집기가 그것을 동기로 훑다가 아무것도 못 찾는다.
  → 그동안 **코드블럭이 있는 `.mdoc` 글은 `render()` 의 `headings` 가 조용히 빈 배열**이었다.
  그래서 `.mdoc` 이 쓰는 코드블럭 언어를 빌드 시작 전에 스캔해 미리 로드하고(`src/shiki/fence-languages.ts`),
  트랜스폼에서는 동기 조회만 한다. 스캔에 없는 언어가 나오면 경고를 남기고 plaintext 로 떨어진다.
- 헤딩 앵커는 **자식이 없는 `<a>`** 이고 보이는 `#` 는 CSS 가 그린다. 텍스트를 넣으면 렌더러가
  헤딩 텍스트를 모을 때 섞여 들어가 목차 텍스트를 오염시키기 때문이다. 대신 CSS 가 없으면
  앵커가 보이지 않는다(헤딩 id 자체는 그대로라 직접 링크는 계속 동작한다).
- 읽기 시간 상수(500자/분·200단어/분·40줄/분)는 **추정치**다. 실제 독자 데이터로 검증한 값이 아니다.
  조정하려면 상수만 고치고 테스트 기대값을 갱신하면 된다.

### 후속 작업

- NOR-24(베이스 테마)에서 목차를 고정 배치로 옮긴다면 스크롤 스파이를 다시 판단한다.
- NOR-29(JSON-LD)는 `derivePostDetail` 의 `publishedISO` / `updatedISO` / `readingTime.iso` /
  `toc` 를 그대로 쓴다. 자세한 매핑표는 `src/lib/post-detail.ts` 주석에 있다.
