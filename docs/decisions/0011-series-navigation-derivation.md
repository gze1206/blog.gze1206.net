# 0011. 시리즈 내비게이션 — 이전/다음 산출 기준과 목록 분량 정책

## 맥락 (Context)

NOR-18 은 글 상세 본문 뒤에 **시리즈 목록·이전/다음 이동·진행도(N/총)** 를 붙인다.
이 세 값이 한 화면에 같이 나오기 때문에, 산출 기준을 하나로 고정하지 않으면 서로 어긋난다.

문제를 만드는 것은 **draft** 다. `seriesOrder` 는 저자가 손으로 매기는 번호이고,
그중 일부는 `draft: true` 라서 프로덕션 빌드에 **페이지 자체가 없다**(ADR 0009).

> `seriesOrder` 1·2·3·4 중 3편이 draft 라면, 2편의 "다음 편"을 `seriesOrder + 1` 로 구하는 순간
> `/blog/<3편>` 이라는 **없는 페이지로 가는 링크**가 만들어진다.

여기에 더해 두 가지를 정해야 한다.

- 시리즈 글 목록을 본문 바로 뒤에 통째로 펼치면 20편짜리 시리즈에서 독자가 벽을 만난다.
- 노출 대상이 1편뿐인 시리즈에서 "1/1" 진행도와 한 줄짜리 목록이 정보인가.

## 검토한 대안 (Options)

### 이전/다음 산출 기준

- **A안 — 원본 `seriesOrder` 의 ±1**
  - 장점: 저자가 매긴 번호와 화면의 편 번호가 언제나 일치한다.
  - 단점: draft 를 만나면 **404 링크**가 생긴다. 번호가 띄엄띄엄(1,2,5)이면 아예 못 찾는다.
    "3편이 비어 있으니 4편을 보라"는 보정 로직이 필요해지고, 그 보정은 결국 B안의 재구현이다.
- **B안 — 노출 대상만 걸러낸 목록의 인접(채택)**
  - 장점: 링크가 존재하는 페이지만 가리킨다. 목록·이전/다음·진행도가 **같은 배열 하나**에서 나온다.
  - 단점: 화면의 편 번호가 저자의 `seriesOrder` 와 다를 수 있다(3편이 draft 면 4편이 "3편"으로 보인다).
- **C안 — draft 를 회색 비활성 항목으로 목록에 남긴다**
  - 장점: 저자의 번호가 그대로 유지된다.
  - 단점: 독자에게 "아직 없는 글"을 알리는 것은 정보가 아니라 소음이고, 미공개 제목이 새어 나간다.

### 목록 분량

- **A안 — 전부 펼친다**: 20편 시리즈에서 본문 뒤에 20줄짜리 벽이 생긴다.
- **B안 — 상한 N편만 보여주고 나머지는 "더 보기"**: 어디가 잘렸는지 독자가 알 수 없고, 현재 글이
  잘린 구간에 있으면 강조가 보이지 않는다. 잘린 목록은 순서 정보를 반쯤 잃는다.
- **C안 — `<details>` 로 접는다(채택)**: 기본 상태만 길이에 따라 정하고, 열면 전부 보인다.

### 노출 대상 1편 시리즈

- **A안 — "1/1" 과 한 줄 목록을 그대로 렌더**
- **B안 — 블록 전체 미렌더(채택)**

## 결정 (Decision)

1. 이전/다음·진행도·목록은 **`getVisiblePosts()` 로 이미 걸러진 목록 하나**에서 파생한다
   (`buildSeriesNav()`). 원본 `seriesOrder` 는 **정렬에만** 쓰고, 인접 관계와 편 번호는
   그 목록의 **인덱스**로 구한다.
2. 시리즈 글 목록은 `<details>` 로 접는다. 노출 대상이 **8편 이하면 `open`**, 그보다 길면 접힌 채로
   시작한다. 잘라내기(truncation)는 하지 않는다.
3. 시리즈의 **노출 대상이 1편뿐이면 블록 전체를 렌더하지 않는다**(`buildSeriesNav` 가 `null`).
4. 이전/다음이 없는 쪽은 **자리 자체를 만들지 않는다**. 비활성 버튼을 두지 않는다.

## 근거 (Rationale)

**(1)** "노출 대상"의 정의는 이미 `selectVisible()` 하나가 갖고 있다(ADR 0009). 인접 관계를
그 결과에서 뽑으면 draft 정책이 바뀌어도 고칠 곳이 한 군데다. 반대로 `seriesOrder ±1` 은
draft·번호 공백이라는 두 가지 이유로 각각 보정이 필요하고, 그 보정은 결국 "존재하는 것만 모아서
앞뒤를 본다"와 같은 말이다. 부작용인 "화면 번호 ≠ 저자 번호"는 받아들인다 —
`/series/[slug]` 페이지도 이미 `index + 1` 을 "N편"으로 쓰고 있어 두 화면이 서로 일치하고,
독자에게 의미 있는 것은 저자의 내부 번호가 아니라 **읽을 수 있는 글 사이의 순서**다.

dev 서버(draft 노출)와 프로덕션에서 진행도 숫자가 달라지는 것은 **입력이 다르기 때문**이며,
한 페이지 안에서는 언제나 셋이 같은 배열에서 나오므로 서로 어긋나지 않는다.

**(2)** `<details>` 는 JS 없이 동작하고 `<summary>` 가 기본 포커스 대상이라 키보드로 열린다.
"정적 우선 · 점진적 향상"(AGENTS.md)에 그대로 맞는다. 상한을 두고 잘라내는 B안은 목록의 존재
이유(순서를 한눈에)를 깎으면서 "현재 글이 목록에 없는" 상태를 만들 수 있어 버렸다.
경계값 8편은 접힌 상태의 정보 손실과 펼친 상태의 길이를 맞바꾼 값이다 — 8줄은 본문 뒤 한 화면을
넘기지 않고, 대부분의 시리즈가 여기 들어온다. 그보다 길면 접어서 "본문 흐름"을 우선한다.

**(3)** 노출 대상이 1편이면 이전/다음이 둘 다 없어 **내비게이션이 아무 데도 데려가지 못한다.**
남는 것은 자기 자신 한 줄과 "1/1" 뿐이고, 시리즈 소속이라는 사실은 상세 헤더가 이미
이름 + 링크로 알려준다(NOR-16). 즉 이 블록은 중복만 남는다.

**(4)** 비활성 버튼은 포커스 순서에 들어가거나(그러면 아무 일도 안 하는 포커스 대상이 생기고),
빠지면(그러면 시각적으로만 존재하는 유령이 된다) 둘 다 손해다. 없으면 없는 대로 두는 편이
스크린리더에도, 눈으로 훑는 독자에게도 정직하다.

## 영향 (Consequences)

- 긍정: 시리즈 내비게이션에 **깨진 링크가 원리적으로 생기지 않는다**(존재하는 페이지 목록에서만 뽑는다).
- 긍정: 목록·이전/다음·진행도가 한 함수의 한 배열에서 나와 셋이 어긋날 수 없다.
- 부정/비용: 화면의 편 번호가 저자의 `seriesOrder` 와 다를 수 있다. 저자가 draft 를 공개하면
  번호가 밀린다(공개 후 안정된다). 편 번호를 영구 식별자로 쓰면 안 된다.
- 부정/비용: dev 와 프로덕션의 진행도 숫자가 다르다. 의도된 차이이며 spec 에 명시했다.
- 후속: Phase 7(JSON-LD, NOR-29)에서 시리즈를 구조화 데이터로 내보낼 일이 생기면
  `buildSeriesNav()` 의 결과를 그대로 쓴다. 별도 계산을 다시 만들지 않는다.
