# 0009. 블로그 라우팅 · 슬러그 · draft 처리 전략

## 맥락 (Context)

NOR-16 에서 처음으로 실제 블로그 라우트(`/blog`, `/blog/[slug]`, `/category`, `/tags`, `/series`)를 만든다.
그 전까지 라우트는 플레이스홀더 `index.astro` 와 `smoke/*` 뿐이었다. 여기서 정하는 URL 구조와
콘텐츠 규칙은 **뒤집기 비싸다** — 발행된 URL 은 바뀌면 링크가 깨지고, NOR-17/18(상세 강화·시리즈
내비게이션)과 NOR-27~30(canonical·사이트맵·RSS·JSON-LD)이 전부 이 위에 얹힌다.

결정해야 할 것이 다섯 가지다.

1. 글의 URL 식별자를 무엇으로 할 것인가 — 프론트매터 `slug` vs 파일명(`entry.id`).
2. 자유 문자열인 `category`·`tags` 를 어떻게 URL 슬러그로 바꿀 것인가 (한글 태그 포함).
3. `draft: true` 를 어디서 어떻게 제외할 것인가.
4. 목록 페이지네이션의 URL 형태와 페이지 크기.
5. 글이 0개인 분류/시리즈, 존재하지 않는 슬러그의 동작.

제약:

- 정적 사이트(`output: 'static'`)라 모든 경로가 빌드타임에 결정된다.
- 스키마(`src/content/schemas.ts`)상 `slug` 는 `^[a-z0-9]+(?:-[a-z0-9]+)*$`, `category`·`tags` 는
  **제약 없는 문자열**이다.
- 규약상 `draft: true` 는 "목록·피드·사이트맵 어디에도 노출 금지"
  ([content-a11y-seo.md](../conventions/content-a11y-seo.md)).

## 검토한 대안 (Options)

### 1. URL 식별자

- **A. 프론트매터 `slug`** — 완료 조건이 요구하는 "영문 슬러그". 파일명을 자유롭게 쓸 수 있고
  (`2026-03-01-회고.md` 같은 정리용 이름 가능), 파일을 옮겨도 URL 이 안 변한다.
  단점: 파일명과 URL 이 어긋나 헷갈릴 수 있다.
- **B. 파일명(`entry.id`)** — 파일 = URL 이라 직관적. 단점: 스키마의 `slug` 필드가 죽은 필드가 되고,
  파일명 규칙을 한글/날짜 접두사 없이 강제해야 한다.

> **조사 중 확인한 사실**: Astro 의 `glob()` 로더는 프론트매터에 `slug` 가 있으면 **그것을 엔트리 `id`
> 로 사용한다**. 즉 A/B 는 실제로는 이미 A 로 통일돼 있고, 문제는 slug 가 겹칠 때 로더가
> **경고(WARN)만 남기고 나중 글로 앞 글을 덮어쓴 채 빌드가 성공한다**는 점이다. 글 하나가 조용히 사라진다.
> 컬렉션 조회 시점에는 이미 사라진 뒤라 `getCollection()` 결과만으로는 검출이 불가능하다.

### 2. category / tags 의 URL 슬러그

- **A. 유니코드 보존 슬러그화** — 소문자화 + NFKC + 공백류→`-` + 기호 제거, **문자·숫자는 유니코드
  전체를 보존**. `웹 성능` → `웹-성능`. 장점: 표시 원문과 URL 이 눈으로 이어진다. 단점: URL 에
  퍼센트 인코딩이 들어간다.
- **B. 로마자 음차** — `웹 성능` → `web-seongneung`. 장점: ASCII URL. 단점: 음차 라이브러리 의존,
  표기 규칙 논쟁, 원문과 URL 이 눈으로 안 이어진다.
- **C. ASCII 만 허용(스키마 제약)** — 가장 단순하지만 한글 태그를 아예 못 쓴다. 한국어 블로그에서
  `회고`, `웹 성능` 을 못 쓰는 건 실질적 손해다.

어느 쪽이든 **서로 다른 표시 문자열이 같은 슬러그로 떨어지는 충돌**(`TypeScript` vs `typescript`,
`C#` vs `C`)을 어떻게 할지 정해야 한다: 조용히 병합 vs 빌드 실패.

### 3. draft 제외

- **A. 항상 제외** — dev 에서도 초안을 못 본다. 브라우저로 초안을 확인할 방법이 사라진다.
- **B. dev 노출 / build 제외** — 초안을 개발 서버에서 확인할 수 있다. 단, dev 와 프로덕션의 목록
  내용·페이지 수가 달라진다.
- 어느 쪽이든 필터가 라우트마다 흩어지면 반드시 한 곳이 빠진다.

### 4. 페이지네이션 URL

- **A. `[...page].astro` (rest 파라미터)** — 1페이지 `/blog`, 2페이지부터 `/blog/2`. `/blog/1` 은
  생성되지 않는다.
- **B. `[page].astro`** — `/blog/1`, `/blog/2`. `/blog` 를 따로 만들면 `/blog` 와 `/blog/1` 이
  **같은 내용의 서로 다른 URL** 이 된다(중복 콘텐츠).
- **C. `/blog/page/2`** — 충돌 위험이 없지만 1페이지를 별도 라우트로 만들어야 해서 목록 로직이 둘로 갈린다.

### 5. 빈 분류 / 없는 슬러그

- **A. 빈 조합도 페이지 생성** — `/tags/없는태그` 가 200 을 준다. 얇은 페이지가 늘고 SEO 에 불리.
- **B. 생성하지 않음** — 존재하지 않는 경로는 404. 정적 사이트의 자연스러운 기본값.

## 결정 (Decision)

1. **URL 식별자는 프론트매터 `slug`** 를 쓴다(A). 그리고 slug 중복은 **원본 파일 텍스트를 직접 훑어**
   빌드타임에 실패시킨다.
2. **유니코드 보존 슬러그화**(A)를 쓴다. `#`·`+` 는 `sharp`/`plus` 로 음차한다(`C#` → `c-sharp`).
   **서로 다른 표시 문자열이 같은 슬러그가 되면 빌드를 실패**시킨다.
3. **dev 노출 / build 제외**(B). draft 필터는 `selectVisible()` **한 함수**만 쓰고, 모든 라우트는
   `src/lib/content.ts` 를 통해서만 글을 가져온다.
4. **rest 파라미터**(A). 1페이지는 `/blog`, 2페이지부터 `/blog/2`. **페이지 크기는 10**.
5. **파생 경로는 글이 있을 때만 생성**(B). 인덱스 페이지(`/blog`, `/category`, `/tags`, `/series`)는
   항상 존재하고, 비면 빈 상태 UI 를 보여준다.

## 근거 (Rationale)

### 1. 슬러그의 단일 출처

완료 조건이 "영문 슬러그"를 요구하고, 스키마가 이미 `slug` 를 정규식으로 강제한다. 파일명을
자유롭게 두면 `fixture-typescript-strict.md` 처럼 정리용 이름을 쓰면서 URL 은
`/blog/typescript-strict-tips` 로 안정시킬 수 있다.

중복 검출을 **컬렉션이 아니라 원본 파일**에서 하는 것이 이 결정의 핵심이다. 로더가 slug 를 id 로
쓰기 때문에, `getCollection('posts')` 를 받아든 시점에는 겹친 글 하나가 이미 사라져 있다.
그래서 `import.meta.glob(..., { query: '?raw' })` 로 원본 텍스트를 읽어 프론트매터의 `slug:` 줄을
직접 비교한다(`assertUniqueSourceSlugs`). 경고를 놓치는 사람은 있어도 실패하는 빌드를 놓치는
사람은 없다.

숫자만으로 된 slug(`/blog/2`)는 페이지네이션 경로와 충돌하므로 별도로 막는다
(`assertPaginationSafeSlugs`). `[slug].astro` 와 `[...page].astro` 가 한 디렉터리를 공유하는 대가다.

### 2. 슬러그 충돌은 병합이 아니라 실패

`TypeScript` 와 `typescript` 가 같은 슬러그로 조용히 합쳐지면 **표시 라벨은 하나만 살아남고**
독자는 자기가 무엇을 보고 있는지 알 수 없다. 이건 대개 표기 실수이고, 실수는 빌드가 알려주는 게 싸다.
`#`·`+` 음차는 이 실패가 **부당하게** 터지는 걸 막는다 — 기호를 그냥 버리면 `C#` 과 `C` 가 충돌하는데,
이건 표기 실수가 아니라 정당한 서로 다른 태그다. .NET 을 다루는 블로그에서 `C#` 태그는 사실상 확정이다.

한글 태그는 한글 슬러그가 된다(`웹 성능` → `웹-성능`). 브라우저 주소창에는 한글로 보이고,
HTML `href` 와 정적 파일 경로에는 퍼센트 인코딩된 UTF-8 이 들어간다(`/tags/%EC%9B%B9-%EC%84%B1%EB%8A%A5`).
로마자 음차(B)를 고르지 않은 이유는 음차 규칙이 결정적이지 않고(국어의 로마자 표기법조차 이형이 많다)
표기 논쟁이 콘텐츠 작성 흐름에 끼어들기 때문이다. 실제 빌드로 `dist/tags/웹-성능/index.html`,
`dist/category/회고/index.html` 이 생성되고 dev 서버에서 200 을 주는 것을 확인했다.

### 3. draft — dev 노출, build 제외

초안을 브라우저로 확인할 수 없으면 CMS(NOR-19/20)에서 글을 쓰는 흐름이 불편해진다. 반면
프로덕션에 draft 가 새는 것은 절대 안 된다. 그래서 `import.meta.env.DEV` 로 갈린다.

여기서 중요한 건 **목록에서 숨기는 것으로는 부족**하다는 점이다. `/blog/[slug]` 의
`getStaticPaths()` 자체가 노출 대상 글만 받으므로, 프로덕션 빌드에는 draft 글의 **페이지가 존재하지
않는다**. URL 을 알아도 볼 수 없다.

dev 와 프로덕션의 목록 내용이 달라지는 것은 감수한다. 대신 **무결성 검사(slug 중복·시리즈 참조·
분류 충돌)는 draft 를 포함한 전수를 대상으로** 한다 — 그래야 "dev 에서는 되는데 배포 빌드만 깨지는"
상황이 생기지 않는다.

### 4. 페이지네이션

`/blog` 와 `/blog/1` 이 둘 다 존재하면 같은 내용에 URL 이 두 개다. canonical 을 붙이기 전에
구조적으로 하나만 만드는 편이 낫다. rest 파라미터는 Astro 가 이 형태를 1급으로 지원한다.

페이지 크기 10 — 카드 하나가 제목·설명·날짜·태그로 대략 8–10줄이라 10개면 모바일에서 스크롤
3–4화면이다. 5는 페이지 이동이 잦고, 20은 목록이 길어져 훑기가 어렵다. Astro `paginate()` 의
기본값과도 같아 예외를 만들지 않는다. 총 페이지 수는 **draft 제외 후** 개수로 계산된다
(제외를 목록 생성 전에 하기 때문에 자동으로 그렇게 된다).

카테고리·태그·시리즈 하위 페이지는 페이지네이션하지 않는다. 한 분류에 수십 편이 쌓이면 그때
같은 방식으로 도입하면 되고, 지금 넣으면 검증할 수 없는 코드가 는다.

### 5. 빈 조합

정적 사이트에서 존재하지 않는 조합에 URL 을 주는 것은 얇은 페이지를 스스로 만드는 일이다.
카테고리·태그는 **글에서 파생**되므로 애초에 빈 페이지가 생길 수 없다. 시리즈는 `series/index.json`
에 정의된 **저작된 엔티티**라 글이 0편일 수 있는데, 이 경우 페이지를 만들지 않고 `/series` 인덱스에서도
빼기로 했다. 인덱스 4개(`/blog`, `/category`, `/tags`, `/series`)는 내비게이션 대상이라 항상 존재하고,
비었을 때는 빈 상태 문구를 보여준다.

## 영향 (Consequences)

- 긍정
  - URL 구조가 확정돼 NOR-17/18/27~30 이 그 위에 얹힐 수 있다. 조회 로직은 `src/lib/content.ts`
    하나로 모여 있어 재사용된다.
  - 콘텐츠 계약 위반(slug 중복·시리즈 오타·분류 표기 흔들림)이 **경고가 아니라 빌드 실패**로 드러난다.
  - draft 가 프로덕션 산출물에 존재할 수 없다 — 목록이 아니라 라우트 생성 단계에서 걸러지기 때문이다.
- 부정/비용
  - dev 와 프로덕션의 `/blog` 페이지 수가 다르다(현재 dev 3페이지 / build 2페이지). 혼동 가능.
  - slug 중복 검사를 위해 글 원본을 `?raw` 로 한 번 더 읽는다. 글 수가 수백 편 되면 빌드 시간에
    영향이 있을 수 있다(현재 21편, 무시할 수준).
  - 프론트매터 `slug:` 는 한 줄에 평범한 스칼라로 적어야 한다(블록 스칼라 등은 파싱 실패로 빌드가
    멈춘다). 실질적 제약은 아니다.
  - 한글 슬러그는 `dist/` 에 한글 디렉터리를 만든다. 배포 대상(Cloudflare Pages)은 UTF-8 경로를
    처리하지만, 다른 호스팅으로 옮길 때 확인이 필요하다.
- 후속 작업
  - NOR-17/18 은 `src/layouts/PostLayout.astro` 의 `<slot name="after-content">` 와
    `src/lib/content.ts` 를 확장해서 붙인다.
  - NOR-26 에서 커스텀 404 를 만든다. 지금은 호스팅 기본 404 다.
  - NOR-27~30 은 `astro.config.mjs` 의 `site: 'https://gze1206.net'` 를 전제로 canonical/사이트맵/RSS 를 만든다.
  - NOR-35(콘텐츠)에서 이번에 넣은 **픽스처 글 11편**을 실제 글로 교체하거나 제거한다.
