# 0008. 커스텀 블럭 데이터 취득 전략 — 빌드타임 fetch + 온디스크 캐시 + 폴백

## 맥락 (Context)

NOR-15의 커스텀 블럭 중 두 개는 **외부 데이터에 의존**한다.

- `{% bookmark url=... /%}` — 대상 페이지의 OG 메타(제목·설명·대표 이미지·사이트명)로 프리뷰 카드를 그린다.
- `{% github repo=... /%}` — GitHub REST API로 레포 설명·스타 수·언어를 가져와 카드를 그린다.

이 저장소의 1순위 원칙은 [`content-a11y-seo.md`](../conventions/content-a11y-seo.md) 의 **"크롤러도 사람도 읽는 정적 콘텐츠"** 다. 동시에 외부 네트워크는 신뢰할 수 없다 — 타임아웃, 404, GitHub 미인증 API의 시간당 60회 제한, 사설/오프라인 URL이 모두 현실이다. **어떤 실패도 빌드를 깨뜨려서는 안 된다.**

## 검토한 대안 (Options)

### 데이터 취득 시점

- **A안: 빌드타임 fetch** — Astro 컴포넌트 frontmatter(정적 빌드에서 빌드타임에 1회 실행)에서 fetch 해 정적 HTML에 굽는다.
  - 장점: 런타임 JS 0, 크롤러가 카드 내용을 읽음, CLS 없음, 방문자 IP가 외부로 새지 않음.
  - 단점: 빌드가 네트워크에 의존, 빌드 시간 증가, 데이터가 빌드 시점에 고정(스타 수가 실시간이 아님).
- **B안: 런타임 클라이언트 fetch** — 브라우저에서 카드 내용을 채운다.
  - 장점: 항상 최신, 빌드 무의존.
  - 단점: 프라이버시(방문자 IP가 대상 사이트로 노출), CORS/프록시 필요, CLS 유발, 크롤러가 빈 카드를 봄. **정적 우선 원칙 정면 위배.**
- **C안: 별도 사전 생성 스크립트 + JSON 커밋** — 수동으로 메타를 긁어 저장소에 커밋.
  - 장점: 빌드 완전 무의존.
  - 단점: 글 쓸 때마다 수동 단계 추가. 저자 경험이 나쁘고 누락되기 쉽다.

### 반복 빌드 비용

- **A안: 온디스크 캐시(TTL)** — fetch 결과를 로컬 디스크에 JSON으로 캐시하고 TTL 내에는 재사용.
- **B안: 캐시 없음** — 매 빌드마다 전부 재요청. 미인증 GitHub API 60 req/h 에 쉽게 걸리고 로컬 반복 빌드가 느려진다.
- **C안: 캐시를 저장소에 커밋** — CI에서도 히트하지만, 외부 사이트의 설명/스타 수가 diff에 섞여 리뷰 노이즈가 되고 캐시가 진실의 원천처럼 보인다.

### 실패 시 동작

- **A안: 우아한 폴백** — 예외를 삼키고 경고 로그만 남긴 뒤 최소 형태(URL/`owner/repo` 문자열 링크)로 렌더.
- **B안: 빌드 실패** — 외부 사이트 장애가 곧 배포 실패. 개인 블로그에 과한 결합.

## 결정 (Decision)

**빌드타임 fetch(A) + TTL 온디스크 캐시(A, 커밋하지 않음) + 실패 시 우아한 폴백(A)** 을 채택한다. 런타임 클라이언트 fetch는 금지한다. 저자가 속성으로 명시한 값은 언제나 fetch 결과를 이긴다.

## 근거 (Rationale)

### 왜 빌드타임인가

정적 우선 원칙이 결정적이다. 카드 제목·설명이 정적 HTML에 있어야 크롤러가 읽고, 검색 결과에 문맥이 남고, 방문자 브라우저가 제3자 도메인에 요청을 보내지 않는다. 이미지 크기/자리 예약도 빌드타임에 고정할 수 있어 CLS가 없다. 스타 수가 실시간이 아닌 것은 블로그 글이라는 맥락에서 허용 가능한 트레이드오프다(글은 시점의 기록이다).

### 캐시 위치·TTL·gitignore

| 항목        | 값                                                                    |
| ----------- | --------------------------------------------------------------------- |
| 위치        | `node_modules/.cache/blocks/` (env `BLOCK_CACHE_DIR`로 덮어쓰기 가능) |
| TTL(북마크) | 30일                                                                  |
| TTL(GitHub) | 24시간                                                                |
| TTL(실패)   | 1시간                                                                 |
| gitignore   | 커밋하지 않음 (`node_modules/` 가 이미 무시됨)                        |

- **위치**: `node_modules/.cache/` 는 빌드 도구들이 캐시를 두는 관례적 위치이며, 이미 `.gitignore` 에 `node_modules/` 가 있어 별도 규칙 없이 커밋에서 배제된다. 저장소 루트를 새 점(dot) 디렉토리로 어지럽히지 않는다. `pnpm install` 로 초기화돼도 캐시는 그저 미스가 될 뿐이라 안전하다.
- **TTL 비대칭**: 북마크의 OG 메타(제목·설명)는 거의 변하지 않으므로 길게(30일), GitHub 스타 수는 자주 변하므로 짧게(24시간) 잡는다. 실패는 1시간만 캐시해서 일시적 장애가 오래 붙잡히지 않게 하되, 한 빌드 안에서 같은 URL을 반복 때리지 않도록 한다.
- **실패도 캐시한다(negative caching)**: 폴백이 정상 경로이므로 실패 역시 결과다. 죽은 링크가 매 빌드마다 타임아웃만큼 빌드를 지연시키는 것을 막는다.
- **커밋하지 않는 대가**: CI(Cloudflare Pages)는 매번 새 체크아웃이라 캐시가 콜드다. 이는 의도한 선택이다 — CI 1회 빌드의 요청 수는 글에 쓰인 블럭 수 정도이고, 저자가 반복 빌드하는 로컬에서 캐시 효과가 가장 크다. CI에서도 아끼고 싶어지면 파이프라인 캐시 스텝으로 이 디렉토리를 보존하면 되고, 그때 저장소를 오염시키지 않은 것이 이득이 된다.

### 명시 속성 우선 (author override)

`{% bookmark url="https://intranet.example" title="사내 위키" /%}` 처럼 저자가 값을 넣으면 **fetch를 아예 건너뛴다.** 이것이 오프라인·사설 URL·의도적 문구 교정에 대한 탈출구다. 네트워크에 닿을 수 없는 대상도 항상 온전한 카드로 렌더할 수 있다.

### GitHub 인증

`GITHUB_TOKEN` 환경변수가 있으면 `Authorization: Bearer` 헤더를 붙여 5,000 req/h 를 쓰고, 없으면 미인증(60 req/h)으로 동작한다. **없다고 실패하지 않는다** — 미인증으로도 대부분의 개인 블로그 빌드는 한도 안이며, 걸리면 폴백이 받아준다. 토큰은 커밋하지 않고 CI 시크릿/로컬 환경변수로만 주입한다.

### 타임아웃

모든 외부 요청에 `AbortSignal.timeout(5000)` 을 건다. 무한 대기는 CI를 잡아먹는 가장 흔한 실패 모드다.

## 영향 (Consequences)

- 긍정: 런타임 JS 0 · 방문자 프라이버시 보존 · 크롤러가 카드 내용을 읽음 · CLS 없음 · 오프라인/네트워크 장애에서도 빌드가 성공.
- 부정/비용:
  - 빌드가 네트워크 지연에 영향을 받는다(블럭당 최대 5초, 캐시 미스 시). 캐시로 완화.
  - 스타 수·설명이 빌드 시점 스냅샷이다. 최신화하려면 재빌드가 필요하다.
  - 데이터 없이 렌더된 폴백 카드는 정보량이 적다. 중요한 링크라면 저자가 `title`/`description` 을 명시하는 것이 정답이다.
  - CI는 캐시 콜드 — 의도한 트레이드오프(위 참고).
- 후속 작업:
  - NOR-20(Keystatic 삽입 UI)이 이 태그 스키마를 그대로 매핑한다. 스키마 정의는 [`docs/spec/NOR-15-custom-blocks.md`](../spec/NOR-15-custom-blocks.md) 가 단일 참조점이다.
  - 배포 파이프라인(NOR-31) 구성 시 `GITHUB_TOKEN` 시크릿 주입과 캐시 디렉토리 보존 여부를 결정한다.
